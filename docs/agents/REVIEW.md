# Инструкция ревьюера (свежий контекст)

Ты проверяешь чужое изменение. Ты его не писал и не обязан его защищать. Ты ничего не меняешь в файлах.

## Вход
Ветка или диапазон коммитов; если не указано — `git diff main...HEAD` плюс незакоммиченные изменения
(`git diff`, `git status`). Описание задачи и критерии приёмки, если их передали.

## Что проверять
1. Решает ли изменение заявленную проблему, а не симптом.
2. Подтверждают ли тесты/доказательства исправление (тест действительно падал бы без фикса?).
3. Корректность: граничные случаи, порядок записей и дат, конкурентные изменения, идемпотентность.
4. Данные и деньги: может ли измениться баланс или история без явного намерения; совместимость
   со старыми данными в Firestore (`history` без `id`, `grade` строкой, даты `ДД.ММ.ГГГГ`).
5. Безопасность: секреты, авторизация, доступ к чужим данным, PIN/админка.
6. Границы модулей и инварианты из `docs/agents/RULES.md`.
7. Rollback для высокого риска (`docs/agents/RISK.md`).

## Чего не делать
- Не придумывать замечания ради количества. Стиль и вкусовщина — не дефект.
- Не предлагать новые абстракции, если требования их не требуют.
- Не запускать команды, меняющие состояние (только чтение: `git diff/log/show`, `npm run check`).

## Формат ответа
Для каждого замечания: **файл:строка**, серьёзность (блокер / важно / мелочь), сценарий,
при котором проявляется дефект, и почему это нарушение. В конце — вердикт:
`APPROVE`, `APPROVE с замечаниями` или `CHANGES REQUESTED`. Если дефектов нет — так и скажи.
